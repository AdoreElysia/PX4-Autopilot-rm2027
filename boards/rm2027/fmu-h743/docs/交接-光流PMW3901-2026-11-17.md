## 1. 这个模块是干什么用的

**光流** = 朝下看地面，靠图像在相邻两帧之间移动了多少像素，算出自己相对地面平移了多少。

它和别的定位手段的分工：

- **IMU/加计**：知道自己转了多少，但**不知道自己平移了多少**（加速度积分会发散）。
- **GPS**：室外能给出对地速度，室内没信号。
- **激光测距（本板已有 VL53L0X）**：给**高度**，不给水平速度。
- **光流**：室内、无 GPS 时给**对地水平速度**，这正是 EKF2 缺的那一块。

所以本板补齐光流之后，EKF2 在室内就能同时有「姿态 + 高度 + 水平速度」，可以定点悬停
而不再依赖 GPS。这也是 RM 比赛里打「室内循迹/定点」的基础。

**为什么还要激光测距**：光流单位是「弧度/秒」（角度变化率），要变成「米/秒」必须知道高度。
PX4 的做法是 `sensors` 模块里的 `VehicleOpticalFlow` 把两路数据合起来
（`VehicleOpticalFlow.cpp:352-405` 读测距，`:112` 起读光流）。**没有有效测距，光流数据会被静默丢弃**。

## 2. 硬件：接哪、怎么接

### 2.1 那个 5 孔排针的真相（证据）

2026-11-17 从 EasyEDA 工程 `26.1无人机飞控&电调` / 板 `FMU_1` / PCB1_1 直接读网络名：

| 排针孔位（丝印） | PCB 网络名 | MCU 引脚 | 依据 |
|---|---|---|---|
| GND | `GND` | — | PCB 网络 |
| SCK | `SPI3_SCK` | **PC10** | PCB 网络 + `board.h:466` |
| MISO | `SPI3_MISO` | **PC11** | PCB 网络 + `board.h:464` |
| MOSI | `SPI3_MOSI` | **PB2** (AF7) | PCB 网络 + `board.h:465` |
| PE14 | `TIM1_CH4` | **PE14** | PCB 网络 + 网表 `U1.44` |

也就是说：设计者**把整条 SPI3 都引出来了**，并且额外多给了一根 PE14 当片选用。

> ⚠️ 旧结论已作废：`src/timer_config.cpp:45-48` 与 `board.h:449-451` 过去写
> 「SPI3 空闲」「PE14 悬空单点网络」，那是 **05-06 / 10-06 那版网表**的判断。
> 现版 PCB 上 `TIM1_CH4` 有两个焊盘（`U1.44` + 这个排针），`SPI3_*` 也各有两个焊盘
> ——**已经引到座子上了**。本次已同步修正 `spi.cpp` 的注释。

### 2.2 接线

```
排针（丝印）        模块（9 针）        备注
GND           →   GND
SCK           →   CLK              4 线 SPI，2 MHz，Mode 0
MISO          →   MISO
MOSI          →   MOSI
PE14          →   CS               片选，低有效
—             →   VIN              ★ 3.3V，从排针旁边的 3.3V_H7 焊盘飞线
—             →   RST             3.3V 或悬空（芯片有上电复位）
—             →   MOT             悬空（驱动不用中断）
—             →   VRE             ★ **不要接任何电源**，它是模块 LDO 的输出（≈2V）
```

**为什么 VIN 要飞线、为什么 VRE 不能接电源**（手册 Table 3，Page 8）：

- PMW3901MB **芯片本体 VDD 只允许 1.8~2.1V**，绝对最大 2.1V，3.3V 会烧片；
- 这个紫色小板上自带 LDO，`VIN` 才是它的输入（可以 3.3V），`VRE` 是 LDO 的**输出**，
  提供给芯片 `VDD` 用。所以 VRE 上出现 ≈2V 是正常的，往它上面接 3.3V 等于直灌芯片。

排针不带电，所以必须从 PCB 上找 3.3V。本板 `3.3V_H7` 网络在排针附近有焊盘
（EasyEDA 查询结果：`(402,-232)`、`(515,-232)` 两处，和 5 孔排针同一区域）。

### 2.3 为什么 DRDY/MOT 不接

`PMW3901.hpp:44` 把采样做成固定 10 ms 定时（`ScheduleOnInterval`），
`RunImpl()` 里主动读 `Delta_X/Y` 与 `Squal`，**不依赖 MOTION 中断引脚**。
所以 MOT 悬空完全没问题，板级登记的 `initSPIDevice(..., CS)` 第二个参数（DRDY）留空。

## 3. 软件：改了哪四处

### 3.1 NuttX：`nuttx-config/nsh/defconfig`

```diff
+CONFIG_STM32H7_SPI3=y
+CONFIG_STM32H7_SPI3_DMA=y
+CONFIG_STM32H7_SPI3_DMA_BUFFER=2048
```

**为什么必须改 NuttX 而不只是板级**：`validateSPIConfig()` 是一个 `constexpr` 断言
（`platforms/nuttx/src/px4/stm/stm32h7/include/px4_arch/spi_hw_description.h:39-92`），
它要求「NuttX 开了 SPIx」和「板级 `px4_spi_buses` 里登记了 SPIx」**双向一致**：
只开一边会**编译失败**（报 `SPI bus config mismatch`），不会拖到运行时。

### 3.2 板级：`src/spi.cpp`

```cpp
initSPIBus(SPI::Bus::SPI3, {
    initSPIDevice(DRV_FLOW_DEVTYPE_PMW3901, SPI::CS{GPIO::PortE, GPIO::Pin14}),
}),
```

`DRV_FLOW_DEVTYPE_PMW3901` = `0xB3`（`src/drivers/drv_sensor.h:247`）。
驱动的 `probe()` 拿这个 devtype 去匹配总线登记项（`pmw3901_main.cpp:73` 的
`BusInstanceIterator`），匹配不上就报 `no instance started`。

> ⚠️ SPI 设备槽位上限是 6（`platforms/common/include/px4_platform_common/spi.h:54`），
> 但那是**每条总线各 6 个**。SPI1 已占满 6 个，SPI2 用了 2 个，SPI3 用 1 个 —— 没有冲突。

### 3.3 编译开关：`default.px4board`

```diff
+CONFIG_DRIVERS_OPTICAL_FLOW_PMW3901=y
```

### 3.4 启动行：`init/rc.board_sensors`

```sh
pmw3901 start -s -b 3 -R 0
```

- `-s` = 板载内部 SPI 总线；`-b 3` = `/dev/spi3`。
- `-R 0` = 模块 X 轴对着机头（**装好后要按实际改**，见 §5）。

## 4. 数据链路：光流怎么到 EKF2

这一步最容易踩坑，因为**中间隔了两层**：

```
pmw3901 驱动
   └─→ sensor_optical_flow            （驱动直接发布，含 pixel_flow[2]，单位弧度）

sensors 模块 / VehicleOpticalFlow
   ├─ 订阅 sensor_optical_flow        （VehicleOpticalFlow.cpp:112）
   ├─ 用陀螺积分补 delta_angle        （:128-170）
   ├─ 用测距补 distance_m             （:352-405）
   ├─ 套 SENS_FLOW_ROT / SCALE / MINHGT / MAXHGT / MAXR
   └─→ vehicle_optical_flow           （:227 附近）

EKF2
   └─ 只订阅 vehicle_optical_flow     （EKF2.hpp:358）
```

**结论**：
1. **只起 `pmw3901` 而 `sensors` 崩了 ⇒ EKF 永远看不到光流**，且**不报错**。
2. `VehicleOpticalFlow` 的构造条件是「`sensor_optical_flow` 已被 advertise」
   （`sensors.cpp:486-497`），只在 `sensors` 初始化时检查一次。
   `rc.board_sensors` 早于模块启动，所以**天然满足**，不需要额外动作。
3. **高度源必须有**：`VehicleOpticalFlow.cpp:363` 只接受
   `orientation == ROTATION_DOWNWARD_FACING` 的测距。
   本板 `vl53l0x start -I -b 1 -a 0x29 -R 25` 里的 `-R 25` 正是
   `ROTATION_PITCH_270` = `ROTATION_DOWNWARD_FACING`（`msg/DistanceSensor.msg:40`）
   ⇒ 那行启动同时是光流的**高度源**，两条要一起跑。

## 5. 上板验证步骤（还没做）

### 5.1 先看驱动起没起来

```
pmw3901 status
```

期望：`running`，且 `pmw3901: read` 计数在涨。

- 报 `no instance started` ⇒ 总线/devtype 不匹配：先确认
  `CONFIG_STM32H7_SPI3=y` 与 `spi.cpp` 的登记都在（两处必须同步）。
- 起来了但 `pmw3901: com err` 猛涨 ⇒ 接线/SPI 模式问题。**先量通断，再怀疑模式**：
  驱动的 `probe()` 读 `Product_ID(0x00)` 必须等于 **0x49**（手册 Table 9）。

### 5.2 再确认原始数据在流动

```
listener sensor_optical_flow
```

把模块对着有纹理的桌面（纯白纸/纯色地砖容易测不到），**慢慢**平移模块，
`pixel_flow[0]`（X）和 `[1]`（Y）应该有响应，`quality` 应 > 0。

- 工作距离 **80 mm ~ ∞**（手册 Table 3）——离太近不行，这和 VL53 正好相反。
- 最大 7.4 rad/s（手册 Table 3）；转太快会直接丢帧。

### 5.3 然后确认 sensors 转换了这一层

```
listener vehicle_optical_flow
```

如果 `sensor_optical_flow` 有数据但 `vehicle_optical_flow` 没有 ⇒ 卡在 §4 的两处：
`sensors` 模块没跑，或者没有朝下的有效测距。

### 5.4 定朝向（`-R` 到底填几）

**判定方法**（和 IMU 六面标定一个思路：只动一个轴，看哪个分量动）：

1. 模块**不动**，整机绕 Z 轴**俯视顺时针**转（yaw 正方向）——光流会误以为自己在平移。
   这一步只看符号，不用管大小。
2. 把模块水平**向机头方向**推：期望 `pixel_flow[0]` 为负（成像往后走），
   `pixel_flow[1]` 接近 0。
3. 把模块**向右**推：期望 `pixel_flow[1]` 有确定的符号，`[0]` 接近 0。

若第 2/3 步对不上，按 45° 的整数倍调 `-R`（`ROTATION_YAW_*`，
`src/lib/conversion/rotation.h:53-60`）。

> ⚠️ **`-R` 只能设一处**。`PMW3901.cpp:317-321` 在驱动内部就已经调过
> `rotate_3f(_yaw_rotation, ...)` 把传感器系转到机体系；而
> `sensors/VehicleOpticalFlow.cpp:94` 又会乘一次 `SENS_FLOW_ROT`。
> 两处都非零 = 转两次（差 90/180 度，现象是「能跑但方向怪」，极难查）。
> **约定：朝向一律写在 `-R`，`SENS_FLOW_ROT` 保持 0。**

### 5.5 最后才是 EKF

```
param set EKF2_OF_CTRL 1     # 缺省就是 1（ekf2/params_optical_flow.yaml:5-10）
```

飞行中看 `vehicle_local_position` 的水平速度是否稳。若光流被拒绝，
调 `EKF2_OF_GATE` / `EKF2_OF_N_MIN` / `EKF2_OF_N_MAX`，**别先动 `SENS_FLOW_SCALE`**。

## 7. 回退

三个开关任取其一关掉即可让功能消失，**互不依赖**：

1. `default.px4board` 里注释 `CONFIG_DRIVERS_OPTICAL_FLOW_PMW3901=y`
   ⇒ 驱动不编进固件（固件变小，但 `rc.board_sensors` 那行会报 unknown command，无害）。
2. `init/rc.board_sensors` 里注释 `pmw3901 start -s -b 3 -R 0`
   ⇒ 驱动在固件里但不启动。
3. `src/spi.cpp` 里删掉 `initSPIBus(SPI::Bus::SPI3, ...)` 那一段 **并同时**关掉
   `CONFIG_STM32H7_SPI3` —— 两处必须同进同退，否则 `constexpr_assert` 编译失败。

EKF2 这边不需要动：没有 `sensor_optical_flow` 时 `VehicleOpticalFlow` 根本不会构造
（`sensors.cpp:486-497`），`vehicle_optical_flow` 不发布，EKF 自然退回原来的行为。
